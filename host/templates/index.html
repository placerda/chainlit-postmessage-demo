Production recommendations (what this demo simplifies)

1. Credential passed to the iframe

  • Do not forward the store session cookie. Issue a dedicated widget token from a same-origin backend call.
  • Use a signed JWT with a short expiry (about 60 seconds), an audience bound to the embedded app (aud), the issuer (iss), and a one-time ID (jti) to block replay.
  • Keep the token in memory only. Never put it in the iframe URL, query string, localStorage, or logs.
  • Rotate signing keys and publish them through a JWKS endpoint so the embedded backend can verify signatures without shared secrets.

2. postMessage hardening

  • postMessage is a transport, not authentication. Trust comes only from validating the token on the server.
  • Host: always send with an explicit targetOrigin (never "*") and accept replies only from the embedded origin.
  • Embedded app: check event.origin against an allowlist of store domains per environment (dev, test, prod).
  • Use a versioned message schema (type, version, payload) and ignore anything else.
  • Do not send sensitive data back to the parent. Chainlit 2.9.x replies with target "*".

3. Server-side session validation

  • The embedded backend validates the credential with the commerce platform (GET /api/v1/sessions/current) before using any identity data. The real contract is TBC: accepted credential, returned fields, billTo and shipTo shape.
  • Secure the server-to-server call with managed identity, an API key in Key Vault, or mTLS.
  • Derive authorization (billTo, shipTo, entitlements) from the validated response, never from values sent by the browser.
  • Cache the validation result for the token lifetime only, and fail closed on errors or timeouts.

4. Session inside the iframe

  • Cookies set by the embedded app are third-party cookies. Use Secure; HttpOnly; SameSite=None; Partitioned (CHIPS), or keep the session token in memory and resend it after reloads.
  • Test Safari, Firefox, and Chrome with third-party cookie restrictions enabled.
  • Tie Chainlit threads and history to the validated user (header or custom auth), not only to cl.user_session.
  • Propagate logout and session expiry from the host to the chat, and clear chat state on user change.

5. Framing and browser policy

  • Embedded app: Content-Security-Policy: frame-ancestors https://store.contoso.com so only the store can frame it.
  • Host: frame-src limited to the embedded origin, plus a strict script-src.
  • Use the iframe sandbox and allow attributes to grant only what the chat needs.

6. Platform and operations

  • Secrets and signing keys in Azure Key Vault, accessed with managed identity.
  • Azure Front Door with WAF in front of both apps, custom domains, TLS only.
  • Private endpoints or network isolation for the backend, search, and model services (as in GPT-RAG zero trust).
  • Rate limiting on the token and chat endpoints.
  • Application Insights with correlation IDs across host, iframe, and backend. Log handshake failures without logging tokens.
  • Health probes, autoscale rules, and separate environments with their own origin allowlists.
